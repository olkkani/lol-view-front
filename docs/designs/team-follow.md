## Problem Statement
사용자가 관심 있는 LoL e스포츠 팀을 팔로우해서, 나중에 경기 리스트에서 자신의 팀을 우선적으로 확인할 수 있게 하는 화면. region(리그)별로 그룹된 전체 팀 목록에서 이미 팔로우한 팀("나의 팀")과 팔로우 가능한 팀을 구분해 보여준다.

## What Makes This Cool
region 그룹 + club_name 정렬로 팀이 많아져도 원하는 팀을 빠르게 찾을 수 있는 목록 구조. 버튼 하나로 팔로잉 상태를 바로 전환할 수 있는 즉각적인 인터랙션(아이콘 버튼 `+`/`✓`).

## Constraints (세션에서 드러난 것)
- 기존 스택 그대로: React, TanStack Router/Query, DESIGN.md(Airbnb 계열) 토큰
- 실제 백엔드(`localhost:9031`)를 curl로 직접 확인함(세션 중 프로브): `GET /matches`만 존재, `/teams`, `/clubs`, `/follows`는 전부 404
- `/matches`의 `clubs[]`에는 팀 축약명(`name`: "DK", "T1")만 있고 **region 필드도 club_name(전체명) 필드도 없음** — 리그명(`leagueName`)은 매치 단위 필드지 팀 단위 필드가 아니라서 팀별 region 매핑에 직접 쓸 수 없음
- 팔로우 상태를 저장할 서버 엔드포인트가 없음
- 로그인/인증은 DESIGN.md 제약상 기존 v1(경기 리스트 뷰어) 스코프 밖으로 이미 명시되어 있음 — 팔로우 기능은 사용자 계정 개념을 전제하므로 이 제약과 정면 충돌

## Premises
1. 팀 팔로우 기능에는 백엔드 신규 계약 3종(팀 목록+region 필드, club_name 전체명, 팔로우 상태 저장/조회)이 필요하며 현재 하나도 존재하지 않는다. **합의됨**
2. 팔로우 상태 저장은 사용자 계정과 결합된 개념이라 인증이 선행되어야 하는데, 기존 DESIGN.md는 "로그인은 스코프 밖"이라 명시한다 — 팀 팔로우는 기존 v1 스코프와 정면 충돌한다. **합의됨**
3. 지금까지 세션에서 만든 와이어프레임(2구역 레이아웃, region 그룹, 아이콘 버튼)은 폐기 대상이 아니라 백엔드 계약이 확정될 때까지 "설계 확정 대기" 상태로 보존한다. **합의됨**

## Approaches Considered

### Approach A: 백엔드 요구사항만 정리, 프론트 구현 전면 보류
필요한 API 계약(엔드포인트, 필드, 인증 방식)만 design doc에 명시하고 코드는 전혀 작성하지 않는다.
- Effort: S · Risk: Low
- 기각 이유: 재작업 리스크는 가장 낮지만, mock 기반으로도 컴포넌트 구조/스타일을 미리 검증할 수 있는 여지를 포기하는 셈이라 이번엔 선택하지 않음.

### Approach B: 계약 정리 + mock 데이터로 프론트 프로토타입 완성 (선택됨)
필요한 API 계약을 Open Questions로 명시하는 동시에, 로컬 mock 데이터로 지금까지의 와이어프레임을 실제 React 컴포넌트로 구현한다. 타입은 "백엔드가 실제로 내려주는 것이 확인된 것"과 "프론트가 아직 가정 중인 것"을 어댑터 레이어로 분리해서, 계약이 오면 어댑터/훅만 교체하고 컴포넌트는 건드리지 않도록 만든다.
- Effort: M · Risk: Medium (완화책 포함시 Low에 가까움)
- 장점: 계약이 오면 어댑터만 갈아끼우면 되므로 체감 진행 속도가 빠름. 컴포넌트 구조/스타일링을 미리 검증 가능.
- 단점: mock 필드명이 실제 API와 다를 경우에도 어댑터 계층 덕분에 컴포넌트 재작업은 방지되지만, 어댑터 자체의 재작성은 필요.

### Approach C: 인증 없는 로컬스토리지 버전으로 스코프 축소
서버 저장 대신 클라이언트 로컬스토리지에 팔로우 상태를 저장하고, region/club_name도 프론트 정적 매핑 테이블로 우회.
- 기각 이유: 백엔드 변경 없이 완결되는 장점은 있지만, 정적 매핑 테이블은 팀 변경 시마다 수동 갱신이 필요한 유지보수 부채이고, 기기 간 동기화가 안 되는 "팔로우"는 반쪽짜리 기능이라 나중에 로그인 도입 시 마이그레이션이 필요함.

## Recommended Approach
**Approach B.** 이 프로젝트는 이미 한 번(경기 리스트 뷰어) "가정된 타입으로 먼저 구현 → 실제 스키마와 크게 어긋나 전면 재작업"을 겪었다. 그 교훈을 살려 이번엔 처음부터 어댑터 계층으로 가정 영역을 격리한다.

**폴더 구조:**
```
features/teams/
  types.ts                    # Team 타입 — "확인됨"과 "가정"을 주석으로 명시
  api/
    mockTeams.ts               # region/club_name/팔로우 상태를 가정한 로컬 mock 데이터
    useTeams.ts                 # 훅의 반환 타입만 고정 — 내부는 지금 mockTeams를 읽지만,
                                 # 나중에 실제 API로 교체될 때 컴포넌트는 이 훅의 시그니처만 본다
  components/
    TeamFollowScreen.tsx        # 뒤로가기 헤더 + 2구역 orchestration
    TeamSection.tsx             # "나의 팀" / "팔로우할 팀" 구역 — region 그룹핑 렌더
    TeamRow.tsx                 # 로고 → 이름 → 버튼(+/✓) 한 행
  utils/
    groupByRegion.ts            # region 오름차순 그룹 → club_name 오름차순 정렬
```

**어댑터 경계 (재작업 리스크 완화 — 보장이 아니라 범위를 좁히는 장치):**
- `useTeams()`가 반환하는 타입(`{ myTeams: Team[]; followableTeams: Team[]; toggleFollow: (id) => void }`)은 지금 고정한다. `FollowedTeam`이라는 별도 타입은 두지 않는다 — 팔로우 여부는 `Team.isFollowing: boolean` 하나로 표현하고, "나의 팀"/"팔로우할 팀" 구역 분리는 `useTeams()`가 이 필드로 이미 나눠 반환하는 두 배열(`myTeams`/`followableTeams`)로 처리한다. 별도 타입이 주는 이점이 없어서 뺐다.
- `Team` 타입의 `region`, `clubName`, `isFollowing` 필드는 지금 전부 mock에서 나오지만, 실제 API 응답이 오면 `useTeams.ts` 내부 구현만 바꾸면 된다 — `TeamFollowScreen`/`TeamSection`/`TeamRow`는 전혀 손대지 않는다. **단, 이건 필드 형태(타입 시그니처)가 안 바뀔 때만 성립하는 보장이다.** 만약 실제 API에서 "팀이 region을 0개 또는 여러 개 가질 수 있다"처럼 region의 카디널리티 자체가 mock 가정(팀당 region 정확히 1개)과 다르면, `groupByRegion.ts`와 `TeamSection.tsx`도 함께 손봐야 한다 — 이 경우는 어댑터 경계 밖의 리스크로 명시적으로 인정한다.
- mock 데이터의 `region`은 세션 중 확인한 실제 리그명(LCK/LPL/LEC)을 그대로 쓰고, `clubName`도 세션 중 확인한 실제 팀 축약명(T1, DK, HLE 등)에 대응하는 전체 이름을 붙인다 — 완전히 상상의 데이터가 아니라 이미 확인된 팀 목록 기반의 가정.
- **mock 상태는 세션(페이지 메모리) 전용이다.** `toggleFollow`는 새로고침하면 초기 mock 상태로 돌아간다 — Approach C(로컬스토리지)를 기각했으므로 브라우저 재시작 간 영속성은 이번 스코프에 없다. Success Criteria 검증 시 새로고침하면 토글이 리셋되는 것은 버그가 아니라 의도된 동작.

## Open Questions (백엔드 요구사항 — 실제 계약 확정 전까지 프론트는 mock 유지)
- **팀 목록 엔드포인트**: `GET /teams` 또는 동등한 엔드포인트가 필요. 응답에 `region`(또는 리그 코드) 필드가 팀 단위로 있어야 함 — 현재 `/matches`의 `leagueName`은 매치 단위라 팀별 소속 리그를 안정적으로 역산할 수 없음(팀이 리그를 이적하는 경우 등).
- **club_name(전체명) 필드**: `/matches`의 `clubs[].name`은 "DK", "T1" 같은 축약명뿐. 전체 팀명이 필요하면 `/teams` 응답에 별도 필드(`fullName` 등)로 내려줘야 함.
- **팔로우 상태 저장/조회**: `POST /follows`, `DELETE /follows/{teamId}`, `GET /follows` 같은 엔드포인트 필요. 이는 사용자 식별(로그인)을 전제로 함 — 인증 방식(세션/토큰) 자체가 별도 설계 대상.
- **인증 스코프 결정**: 팀 팔로우를 v1에 포함하려면 로그인이 별도 에픽으로 선행되어야 함. 이번 세션은 이 결정을 강제하지 않고, 백엔드 계약이 오는 시점에 다시 `/office-hours`로 인증 방식을 설계하는 것을 전제로 한다.

## Success Criteria
- mock 데이터 기준으로 **region은 고정 순서(LCK → LPL → LEC — 알파벳순이 아니라 세션 중 확인된 리그 우선순위)**로 그룹되고, 그룹 내부는 club_name 오름차순(알파벳/가나다순)으로 정렬된다. region 자체의 정렬 기준을 알파벳순으로 바꿀 필요가 생기면 이 문서를 갱신한다.
- "나의 팀"과 "팔로우할 팀" 구역이 명확히 분리되고, 버튼 클릭 시 두 구역 사이로 팀이 즉시 이동한다(mock 상태 토글, 새로고침 시 리셋됨 — 위 어댑터 경계 절 참고)
- `useTeams` 훅의 반환 타입 계약을 다른 컴포넌트가 몰라도 되도록 어댑터 경계가 지켜진다 — 실제 API가 mock과 동일한 카디널리티(팀당 region 1개)를 유지하는 한 `useTeams.ts` 외 파일은 diff가 발생하지 않아야 한다
- 뒤로가기 버튼, 아이콘 버튼(`+`/`✓`)이 DESIGN.md 토큰(Rausch, rounded.full) 그대로 구현된다
- 빈 region(팔로우 가능한 팀이 그 리그에 하나도 안 남은 경우), 로딩/에러 상태는 이번 스코프의 mock 프로토타입에서는 다루지 않는다 — mock은 항상 즉시 값을 반환하므로 로딩 상태가 없고, 에러도 발생하지 않는다. 실제 API 연동 시점에 이 상태들을 재설계한다(TODOS.md 후보).

## Next Steps
1. `features/teams/types.ts` — `Team` 타입(`id`, `region`, `clubName`, `isFollowing` 등) 정의. `region`/`clubName`/`isFollowing` 필드에 "mock 기반 가정, 백엔드 계약 확정 시 갱신 필요"라고 주석 명시
2. `features/teams/api/mockTeams.ts` — 세션 중 확인한 실제 팀 축약명(T1, DK, HLE, KT, DNS, NS, BRO, BFX, KRX 등 LCK 팀 + LPL/LEC 예시)에 region/전체명을 붙인 mock 데이터 작성
3. `features/teams/api/useTeams.ts` — 훅 시그니처 고정, 내부는 mockTeams 사용 + 로컬 상태로 toggleFollow 구현
4. `features/teams/utils/groupByRegion.ts` — region 오름차순 그룹 → 그룹 내 clubName 오름차순 정렬 + 유닛 테스트
5. `TeamRow`, `TeamSection`, `TeamFollowScreen` 컴포넌트 구현 (세션에서 확정한 와이어프레임 기준: 로고→이름→버튼 우측 정렬, 아이콘 버튼, 뒤로가기)
6. 라우트 연결 — `/teams` 경로로 신규 라우트 파일(`routes/teams.tsx`)을 만들어 기존 `routes/index.tsx`(경기 리스트)와 분리한다. 두 라우트는 서로 다른 화면이라 종속 관계가 없음 — 세부 네비게이션 진입점(헤더 햄버거 메뉴에서 연결 등)은 `/plan-eng-review`에서 확정.
7. **백엔드 계약이 확정되면**: `mockTeams.ts` 삭제, `useTeams.ts` 내부를 실제 fetch로 교체, `types.ts`의 가정 주석 제거 — 이 세 파일 외에는 변경 없어야 함(어댑터 경계 검증)

## What I noticed about how you think
- 와이어프레임을 세부 조정(버튼 위치, 아이콘화)까지 반복하다가, 리뷰 요청 시점에 스스로 "완성된 프레임워크"라고 표현했다 — 그런데 실제로 curl로 백엔드를 찔러보니 그 완성된 화면이 전제한 데이터(region, 전체팀명, 팔로우 영속화)가 하나도 없었다. 이 세션에서 그 사실을 확인했을 때 "폐기하지 말고 보류하자"는 판단을 바로 받아들인 것은 — 이미 만든 것에 대한 매몰비용에 흔들리지 않았다는 신호.
- "백엔드 확장을 직접 요청하고 이 기능은 보류"를 추천안으로 먼저 골랐다가, 실제로는 mock 프로토타입까지 진행하는 절충안(B)을 선택했다 — 이상적인 순서(계약 먼저)와 실용적 진행(지금 만들 수 있는 것부터) 사이에서 후자를 택하되, 어댑터 경계로 재작업 리스크를 관리하는 균형 감각을 보였다.
