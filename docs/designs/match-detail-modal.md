## Problem Statement
매치 리스트에서 카드를 클릭하면 해당 경기의 상세 정보를 모달로 확인할 수 있어야 한다. 리그/매치명, 진행 상태, 팀 로고/약칭, 현재 스코어, 그리고 리그·토너먼트 불문 최근 5경기 상대전적을 한 화면에서 보여준다.

## What Makes This Cool
"리그/팀 로고 비주얼 완성도가 가장 wow 포인트"라는 사용자의 명확한 우선순위. 클릭한 카드의 로고가 정적으로 새 모달에 다시 그려지는 게 아니라, 그 자리에서 커진 로고로 자연스럽게 이어지는 모션(FLIP/View Transitions)을 통해 이 우선순위를 정적 렌더링이 아닌 모션 연속성으로 승격한다.

## Constraints
- 상대전적 전용 백엔드 엔드포인트는 아직 존재하지 않음 — 이번 스코프는 프론트 계약(타입 + 훅)까지만 확정, 실제 연동은 백엔드 준비 후.
- `Club` 타입에 팀을 식별할 `id` 필드가 없음 — 상대전적 조회의 전제조건.
- 기존 스택(Vite, TanStack Router/Query, Tailwind v4, `@base-ui/react`) 그대로 사용.
- 기존 `?range=` 서치 파라미터 패턴과 일관된 방식으로 모달 상태를 URL에 반영.
- `MatchCard`는 현재 완전히 비인터랙티브(onClick 없음, button/a 아님, `cursor-pointer`·포커스·키보드 핸들링 없음) — 클릭 트리거 추가는 단순 핸들러 연결이 아니라 인터랙션+접근성 표면을 새로 만드는 작업이다.

## Premises
1. 매치 카드 클릭 → 모달이 열리고, 이 상태는 URL(`?matchId=`)에 반영된다. **합의됨**
2. 상대전적은 `clubId` 기반 새 엔드포인트가 필요하며 아직 백엔드에 없다 — 이번 스코프는 프론트 계약까지만 확정. **합의됨**
3. `Club` 타입에 `id` 필드 추가가 필요하다 (name 기반 매칭은 동명이팀 충돌 위험으로 기각). **합의됨 (백엔드 후속 작업 — 이번 라운드의 critical path 아님, Open Questions 참고)**

## Cross-Model Perspective
Codex는 인증 실패(401)로 사용 불가 — Claude 서브에이전트로 폴백.

- **가장 멋진 버전**: 모달을 그냥 열지 말고, 클릭한 카드의 로고/스코어가 그 자리에서 모달의 더 큰 로고로 모핑되는 shared-element transition(FLIP 또는 `view-transition-name`). "로고 비주얼 완성도 = wow" 본능을 모션 연속성으로 끌어올린 버전.
- **가장 흥분한 포인트**: "가장 wow 요소는 리그/팀 로고 비주얼 완성도"라는 답변 — 기능 완성도가 아니라 특정 비주얼/공예적 보상을 쫓고 있음. H2H·엔드포인트 계약은 의무적으로 하는 일이지 흥분 포인트가 아님.
- **오픈소스로 50%**: `@base-ui/react` Dialog(이미 설치됨) + TanStack Router search-param 동기화로 모달 메커니즘 절반은 거의 공짜. FLIP/모핑 트랜지션은 오프더셸프 도구가 없는 진짜 커스텀 작업.
- **주말 빌드 순서**: 라우트 search param 추가 → 모달 컴포넌트(base-ui Dialog) → `MatchCard`에서 navigate 연결 → 로고/스코어 렌더링을 공유 서브컴포넌트로 추출(카드+모달 동시 혜택) → H2H 타입+훅(얇게, 스텁) → H2H 아이콘 행. 메커니즘이 end-to-end로 동작한 뒤 FLIP 트랜지션에 남은 시간 투자.

이 세션에서 새로 채택한 것: FLIP/모핑 트랜지션을 Approach B로 채택. `TeamLogo`/`TeamSlot` 공유 추출 제안도 Approach B에 반영.

## Approaches Considered

### Approach A: 표준 다이얼로그 + 정적 렌더링
`@base-ui/react` Dialog + URL search param(`matchId`)으로 열림/닫힘 관리, 기본 fade/scale 트랜지션만 사용.
- Effort: S · Risk: Low
- 장점: 가장 빠르게 완성, base-ui Dialog가 접근성(포커스 트랩/ESC/오버레이 클릭) 기본 제공
- 단점: 사용자가 지목한 "로고 비주얼" 우선순위에는 다소 못 미치는 밋밋한 전환
- 기각 아님 — Approach B의 기반 메커니즘으로 채택됨

### Approach C: 모달 없이 인라인 확장 (기각)
클릭한 카드가 리스트 안에서 그 자리에 세로로 확장되는 아코디언 스타일.
- 기각 이유: 리그별 그룹핑 레이아웃과 결합도가 높아져 그룹 재배치/스크롤 보존 로직과 충돌 위험. URL 딥링크 시맨틱도 어색함.

## Recommended Approach
**Approach B: 공유 서브컴포넌트 + FLIP 모핑 트랜지션 (선택됨)**

Approach A를 기반 메커니즘으로 먼저 구현하고, `MatchCard`의 `TeamLogo`/`TeamSlot`을 카드와 모달이 공유하는 서브컴포넌트로 추출한 뒤, 클릭한 카드의 로고 위치에서 모달의 확대된 로고로 View Transitions API로 모핑하는 점진적 강화(progressive enhancement)로 설계한다. `document.startViewTransition` 미지원 브라우저(Safari 구버전 등)는 feature-detect 분기를 통해 Approach A의 정적 fade/scale 전환으로 폴백된다.

- Effort: M · Risk: Med
- 장점: 사용자가 명시한 wow 포인트와 정확히 일치, 로고 렌더링 로직 공유로 중복 방지
- 재사용: `DateTabs`의 `validateSearch` 패턴, `MatchCard`의 `TeamLogo`/`TeamSlot`
- **구현상 실제 리스크 (리뷰에서 지적됨):**
  - `document.startViewTransition()`은 same-document DOM 변경을 스냅샷 비교하는 API다. TanStack Router의 search-param navigate + base-ui Dialog의 open 상태 변경을 여기에 수동으로 감싸야 하며(React 18+는 동기 DOM 갱신을 위해 `flushSync` 필요), "지원 브라우저에서 자동으로 동작"이 아니라 명시적 코드 작업이다.
  - base-ui Dialog는 `document.body`에 포탈로 렌더링될 가능성이 높다. FLIP 계산은 카드(리스트 인라인)와 모달(포탈) 사이의 좌표를 모달이 열리기 직전 시점에 캡처해야 하는데, Dialog의 body-scroll-lock 타이밍과 겹치면 좌표가 틀어질 수 있다.
  - `view-transition-name`은 카드의 `TeamLogo`와 모달의 `TeamLogo`가 "같은 요소"로 인식되도록 매치+팀 식별자 기반 값을 공유 서브컴포넌트에 prop으로 전달해야 성립한다(단순히 컴포넌트를 공유하는 것만으론 부족).
  - "수동 FLIP" 폴백은 위 포탈/스크롤락 이슈 때문에 View Transitions보다 오히려 구현 비용이 크다. 이번 스코프는 **View Transitions API만 시도하고, 미지원 브라우저는 Success Criteria에 명시된 fade/scale로 폴백** — 수동 FLIP은 별도 대안으로 시도하지 않는다.
  - `document.startViewTransition` 존재 여부를 feature-detect하는 분기 코드가 필요 — "자연스러운 폴백"은 이 분기가 있을 때만 성립하며 별도 구현 항목이다.

## Open Questions
- 상대전적 엔드포인트(`GET /head-to-head?teamA={id}&teamB={id}&limit=5`)의 실제 백엔드 구현 시점 — 이번 스코프는 프론트 계약까지만, 연동은 별도 후속 작업.
- `Club` 타입에 `id` 필드 추가 — 백엔드 스키마 변경 필요, 이번 세션에서 요청사항으로 확정됨. **단, H2H 자체가 이번 스코프에서 스텁 처리되므로 `id`는 이번 라운드의 critical path가 아니다** — 백엔드 반영 전까지 프론트는 진행 가능.
- 팀 약칭(짧은 이름) 필드가 백엔드 응답에 별도로 존재하는지 미확인. **폴백 규칙**: 별도 필드가 없으면 `name`을 그대로 사용(자르지 않음) — 약칭 전용 필드가 백엔드에 추가되면 교체.
- View Transitions API 미지원 브라우저(구형 Safari 등)에서의 폴백 UX가 Approach A와 시각적으로 충분히 자연스러운지 실제 구현 후 검증 필요.
- 취소/연기된 매치를 상세 모달에서 어떻게 표기할지 — `MatchState`는 열린 문자열 유니온으로 향후 취소 값이 추가될 수 있음을 이미 전제하고 있음. **결정**: 리스트 카드와 동일한 muted 텍스트 배지 규칙을 모달에도 그대로 재사용한다 (Success Criteria에 반영).
- `clubs.length !== 2`(대진 미정)인 매치를 클릭했을 때 모달 동작 — **결정**: 클릭 가능하되, 모달 내부는 카드와 동일하게 "대진 미정" 상태를 렌더링하고 상대전적 섹션은 생략한다.
- `?matchId=`가 현재 로드된 `range`의 목록에 없는 경우(딥링크, 공유 링크, range 전환 후 새로고침) — **결정**: 모달은 자체 fetch 없이 현재 로드된 리스트 데이터에서만 매치를 찾는다(이번 스코프는 range당 1회 fetch + 폴링 캐시 재사용). id가 목록에 없으면 모달을 열지 않고 `matchId`를 조용히 무시한다. 매치 단건 조회 API를 통한 완전한 딥링크 지원은 스코프 밖(향후 개선 항목).
- `matchId`가 숫자가 아닌 값일 경우 — `validateSearch`에서 `range`와 동일하게 화이트리스트 검증 후, 비숫자 값은 없는 것으로 처리(모달 닫힘 상태).

## Success Criteria
- 매치 카드를 클릭하면 모달이 열리고 URL에 `?matchId=`가 반영된다 (뒤로가기/새로고침 시 상태 유지, 단 현재 로드된 리스트에 있는 매치에 한함 — Open Questions 참고).
- 모달 닫기는 X 버튼, ESC, 오버레이 클릭 세 경로 모두 동일하게 `navigate({ search: { matchId: undefined } })`를 호출해 URL과 동기화된다.
- `MatchCard`가 키보드(Enter/Space)와 클릭 양쪽으로 모달을 열 수 있는 인터랙티브 요소(버튼 시맨틱 + focus-visible 스타일)가 된다.
- 모달에 리그명, 매치명, 진행 상태, 양 팀 로고/약칭(약칭 필드 부재 시 `name` 그대로 폴백)이 표시된다.
- 현재 스코어는 `Club.score`(카드에서 쓰는 것과 동일한 필드)를 그대로 재사용한다 — 별도의 세트별 스코어 필드는 이번 스코프에 없다.
- 대진 미정(`clubs.length !== 2`) 매치는 모달에서도 카드와 동일하게 "대진 미정"으로 렌더링되고 상대전적 섹션은 생략된다.
- 취소/연기된 매치는 리스트 카드와 동일한 muted 텍스트 배지 규칙을 모달에도 재사용한다.
- 최근 5경기 상대전적이 승/패 아이콘 5개로 간결하게 표시된다. 백엔드 연동 전까지는 스텁 데이터로 5개의 중립색(회색) dot을 렌더링해 "승패 미상"을 표현한다.
- 카드 클릭 시 로고가 자리에서 모달의 확대된 로고로 자연스럽게 모핑되며(View Transitions API, `document.startViewTransition` 지원 시), 미지원 브라우저에서는 feature-detect 분기를 통해 기본 fade/scale로 우아하게 폴백된다.
- `today` 탭(15초 폴링)에서 라이브 매치의 모달을 열어둔 채로 경기가 종료로 전환되면, 모달이 닫혔다 열리지 않고도 자동으로 최신 상태(종료, 최종 스코어)로 갱신된다 (모달과 리스트가 같은 쿼리 캐시를 공유하는 부수효과).

4. `MatchCard`를 인터랙티브 요소로 전환 — 버튼 시맨틱(또는 `role="button"`) + 키보드(Enter/Space) 핸들링 + focus-visible 스타일 추가, 클릭/키보드 모두 `navigate({ search: { ...prev, matchId: match.id } })` 호출.
5. `Club` 타입에 `id: number` 필드 추가 요청을 백엔드에 전달(별도 트래킹) — 이번 프론트 스코프의 critical path는 아님, H2H가 스텁 상태이므로 병행 가능.
6. `src/features/matches/types.ts`에 `HeadToHead` 타입만 추가: `interface HeadToHead { results: ('W' | 'L')[] }` (최신순, 최대 5개). `useHeadToHead` 훅은 이번 라운드에 생략 — 백엔드 연동 전까지는 미사용 코드 경로를 만들지 않기 위해 H2H 아이콘 행 컴포넌트가 5개 중립색(회색) dot 상수를 직접 렌더링한다. 훅은 백엔드 엔드포인트가 준비된 후 별도로 추가. **정직성 caveat (아웃사이드 보이스 검토)**: 이번 라운드는 이 타입을 실제 데이터로 검증하지 않는다 — `clubId`가 아직 없어 쿼리 키를 구성할 수 없기 때문. "프론트 계약 확정"은 타입 선언이 존재한다는 뜻이지, 실제 응답으로 검증됐다는 뜻이 아니다.
7. H2H 승/패 아이콘 행 컴포넌트 (5개 dot, 고정 회색 상수 렌더 — 미사용 훅 경로 없음).
8. 모달 메커니즘이 end-to-end로 동작 확인 후 — `document.startViewTransition`(React `flushSync`로 감싼 동기 DOM 갱신) 기반 FLIP 모핑 트랜지션 추가. 카드가 리스트 인라인, 모달이 포탈(body)에 렌더링되는 점을 고려해 좌표 캡처 타이밍을 base-ui Dialog의 scroll-lock 시점과 맞춰 검증. `document.startViewTransition` feature-detect 분기로 미지원 브라우저는 정적 fade/scale 폴백. **Fallback trigger (아웃사이드 보이스 검토 후 추가)**: 이 단계는 계획의 가장 리스크 높은 항목이며 스코프 마지막 순서에 배치되어 있다 — 개인 사이드 프로젝트 특성상 시간 내 완성 못 할 수 있음을 인정한다. 이 단계 구현에 예상보다 현저히 많은 시간이 들면(예: 반나절 이상), Approach A의 정적 fade/scale로 내려 마무리하고 View Transitions는 별도 세션으로 미룬다 — "점진적 강화"가 "주말이 끝났을 때의 임의 상태"가 되지 않도록.

## Worktree parallelization strategy
순차 구현, 병렬화 기회 없음 — 모든 단계가 같은 모듈(`src/features/matches/`)을 순차적으로 건드리는 종속성 체인(픽스처 추출 → 라우트 파라미터 → 모달 컴포넌트 → 공유 서브컴포넌트 추출 → 인터랙티브 전환 → 타입 → H2H 컴포넌트 → 트랜지션).
